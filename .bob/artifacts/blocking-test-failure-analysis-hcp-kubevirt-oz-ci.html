Per-Test Root Cause Analysis

1. [sig-builds] imagechangetriggers — trigger builds of all types
fail [imagechangetriggers.go:57]: Unexpected error: <wait.errInterrupted>: timed out waiting for the condition

Root cause: The test creates BuildConfigs (source, docker, custom, jenkins) and waits for builds to be triggered via ImageStreamTag changes. It timed out (41 s) with zero pods created in the namespace — meaning no build pod was ever scheduled. The OpenShift internal image registry is not backed by real images on this IBM Z KubeVirt cluster (no nodejs-ex imagestream exists in the openshift namespace that has a populated tag), so the image-change trigger never fires.

Related to HCP KubeVirt? Yes — this is an IBM Z hosted-cluster running on KubeVirt VMs. The cluster does not have a pre-populated OpenShift imagestream catalog with s390x-native images, which is required by this test to fire the trigger.

Verdict: SAFE TO SKIP — This is a known s390x / hosted-cluster limitation. The test requires a working image-change trigger backed by a real registry pull, which the bare HCP guest cluster doesn't have in this rehearsal environment.

2. [sig-builds] oc new-app should succeed with an imagestream
Error running oc new-app … registry.redhat.io/ubi8/nodejs-16:latest~https://github.com/sclorg/nodejs-ex … error: unable to locate any images in image streams, local docker images with name "registry.redhat.io/ubi8/nodejs-16:latest"

Root cause: oc new-app needs the image to exist either in an ImageStream or be pullable by the cluster. The guest hosted cluster cannot reach registry.redhat.io (no pull-secret seeded), and the openshift namespace imagestreams do not contain ubi8/nodejs-16 for s390x.

Related to HCP KubeVirt? Yes — the hosted guest cluster is not pre-seeded with Red Hat imagestream content, which is a standard limitation of the KubeVirt bare-HCP rehearsal setup.

Verdict: SAFE TO SKIP — Same root cause family as #1. Failing consistently across all rehearsals; not a code regression.

3. [sig-instrumentation][Late] Platform Prometheus targets should not skip TLS CA verification
fail [prometheus.go:217]: fetch Prometheus scrape configuration context deadline exceeded: https://prometheus-k8s-openshift-monitoring.apps.hcpvirt-oz-ci.phc-cicd.cis.ibm.net/api/v1/status/config: request failed: Get "…": context deadline exceeded (Client.Timeout exceeded while awaiting headers)

Root cause: The test connects to the in-cluster Prometheus API endpoint via the ingress route. The route prometheus-k8s-openshift-monitoring.apps.hcpvirt-oz-ci.phc-cicd.cis.ibm.net is unreachable from the test runner — the entire test run shows persistent i/o timeout errors connecting to the console/apps ingress VIP (192.168.2.54:443). This is a network-level issue: the ingress load-balancer IP is not routable from outside the KubeVirt guest network. The Prometheus endpoint never responds, so the test times out in 1m8s.

Related to HCP KubeVirt? Directly. The KubeVirt guest cluster's ingress/load-balancer VIP (192.168.2.54) is on an internal KubeVirt pod-network CIDR that is not externally routable from the CI test runner. This is a fundamental topology constraint of the HCP-on-KubeVirt setup where VMs use an isolated L2 network.

Verdict: SAFE TO SKIP — This test is structurally impossible to pass in this topology. The same ingress timeout also explains the "sig-network" Internet test (#5). Already failing in all rehearsals; not a code issue.

4. [sig-kubevirt] services … LoadBalancer service across different guest nodes
fail [services.go:68]: Interrupted by User Spec goroutine stuck in: service.(*TestJig).WaitForLoadBalancer → launchWebserverLoadBalancerService → k8s.io/apimachinery/pkg/util/wait.PollUntilContextTimeout (Spec Runtime: 14m59.216s — timed out waiting for LoadBalancer IP to become ready)

Root cause: The test creates a LoadBalancer-type service in the KubeVirt guest cluster and waits up to ~15 minutes for an external IP to be assigned and reachable. The LoadBalancer IP never becomes ready — this is because the HCP KubeVirt guest cluster's load-balancer stack is backed by MetalLB or a similar L2 LB mechanism operating on the KubeVirt VM's internal network, and the test's outbound probe from outside the VM network never receives a reply. The test exhausted the full timeout and was killed by the test runner interrupt.

Related to HCP KubeVirt? Directly and specifically — the test is in [sig-kubevirt] and explicitly exercises "KubeVirt virtual machines should allow connections … via LoadBalancer service." The LoadBalancer IP is on the guest-internal network (192.168.x.x) not routable from the test pod.

Verdict: SAFE TO SKIP — This test was designed for a standard KubeVirt environment where the LB IP is reachable. In this IBM Z / HCP-on-KubeVirt topology the LB IP is on an internal L2 and cannot be reached from the conformance test runner. Consistently failing; safe to add to TEST_SKIPS.

5. [sig-network] Networking should provide Internet connection for containers [Feature:Networking-IPv4]
nc: connect to 8.8.8.8 port 53 (tcp) timed out: Operation in progress fail [networking.go:90]: WaitForPodSuccessInNamespace … pod failed to reach success condition

Root cause: The test launches a pod that tries to reach 8.8.8.8:53 (Google DNS) over TCP. The HCP KubeVirt guest cluster VMs are on an isolated internal network with no public internet egress (or egress is blocked at the IBM Z LPAR/hypervisor level). The connection times out — no internet path from the guest pods.

Related to HCP KubeVirt? Yes — the guest VMs run inside a KubeVirt network with no external internet routing. This is an infrastructure topology limitation specific to this environment, not a code bug.

Verdict: SAFE TO SKIP — This test verifies outbound internet connectivity that the environment intentionally does not provide. Identical failure in both runs.

6. [sig-cli] oc builds complex build start-build (Run A only)
Error from server (NotFound): imagestreamtags.image.openshift.io "ruby-27-centos7:latest" not found [FAILED] in [JustBeforeEach] - cli/builds.go:226 @ 10/01/26 03:53:12.827

Root cause: The test's JustBeforeEach hook expects the imagestream tag ruby-27-centos7:latest to exist in the cluster before the test body runs. The imagestream is absent because the guest cluster was not seeded with Red Hat s390x image catalog content. The test fails in setup (JustBeforeEach), not in the test body.

Why only in Run A? Flakiness in test scheduling order — in Run B the suite hit the 5-failure mass-failure threshold before this test could be attempted, or it was skipped by the framework. The underlying cause (missing imagestream) is the same as #1 and #2.

Verdict: SAFE TO SKIP — Same family as imagechangetriggers/#1/new-app/#2. Missing imagestream content in the guest cluster, a consistent environment limitation.

Common Thread & Skip Recommendation

All 6 failures share two root causes:

  • Missing ImageStream content (tests 1, 2, 6) — The guest HCP cluster is not seeded with Red Hat s390x builder imagestreams (nodejs-16, ruby-27-centos7). Build-triggering tests require those images to exist.
  • Network isolation of the KubeVirt guest (tests 3, 4, 5) — The KubeVirt VM internal network (192.168.2.x) is not routable from the conformance test runner. LoadBalancer services, ingress routes, and outbound internet all fail silently with i/o timeout.

None of these failures are caused by the code changes in PR #84152. They are structural environment constraints of the HCP-on-KubeVirt-on-IBM-Z topology. Since they fail in every rehearsal run (>2 runs), it is appropriate to add them to TEST_SKIPS.
