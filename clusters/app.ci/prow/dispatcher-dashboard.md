# Dispatcher dashboard rollout

The dashboard runs in `ci` on app.ci. OpenShift OAuth restricts the HTTPS route to
`test-platform-ci-admins` (and principals otherwise authorized to get the virtual
`ci.openshift.io/dispatcherobservations` resource). Only the OAuth proxy listens
on the dashboard pod's network interface; its application binds to loopback.

## Internal dispatcher access

The dispatcher exposes observations and metrics on a separate HTTPS listener at
`https://prowjob-dispatcher.ci.svc:8443`. The existing port 8080 keeps scheduling,
control, and monitoring traffic and does not expose observation routes. There is
no external Route for the observation listener.

The dashboard uses a pod-bound, hourly rotating ServiceAccount token with audience
`prowjob-dispatcher-observation`. Kubernetes projects this token into the app
container; it is not stored in GSM, mounted into the OAuth proxy, or sent to the
browser. The dispatcher checks it with Kubernetes TokenReview and accepts only
`system:serviceaccount:ci:dispatcher-dashboard`. The dispatcher requires only the
cluster-wide `create tokenreviews` permission for this check, granted in
`03_deployment/admin_prowjob-dispatcher_observation_rbac.yaml`.

The service-ca controller issues the dispatcher's serving certificate and injects
its CA into `dispatcher-observation-ca`. Both applications reload rotated trust
material. The NetworkPolicy permits observation port 8443 from dashboard pods in
`ci` and preserves the existing access to port 8080. NetworkPolicies are additive;
future policies selecting the dispatcher must preserve this restriction. Identity
validation remains mandatory regardless of network access.

The dashboard has read-only pod discovery and pod-log permissions in `ci`, with no
dispatcher control or Secret-read role. Diagnostics collect Kubernetes logs only
on **Collect logs**, with no automatic refresh or background collection. The
only lookback choices are **Last 30 minutes** and **As much as available within
the limit**. The latter has no time cutoff; Kubernetes retention determines
which logs remain available.

`--log-max-bytes=8388608` sets the single collection size limit to 8 MiB, divided
equally between scheduler and dispatcher. Collection reads current main-container
logs and retained previous-container logs after restarts within that budget,
without a separate line-count limit. Fixed pod-discovery, issue-group, and
eight-second request guards keep work bounded. The UI shows bytes read, the
budget, and partial-collection reasons. Deleted pods, older restarts, and logs
already rotated away cannot be recovered; selecting a longer lookback does not
restore missing history. No AWS credentials, permissions, or log archive are used.

## Provision the OAuth cookie key

Only the OAuth session key needs manual provisioning. Use the existing
`test-platform-infra` collection and the
[CI Secret Manager CLI](https://docs.ci.openshift.org/how-tos/adding-a-new-secret-to-ci-gsm/).
Create the field once; reuse an existing value rather than rotating on deployment.
Do not commit it or pass it using `--from-literal`.

Run with a locally installed `sm` CLI and no shell tracing:

```sh
(
  set -eu
  set +x
  umask 077
  dashboard_secret_dir=$(mktemp -d)
  trap 'rm -rf "$dashboard_secret_dir"' EXIT
  openssl rand -base64 32 > "$dashboard_secret_dir/session-secret"
  sm create -c test-platform-infra dispatcher-dashboard-oauth/session-secret \
    --from-file="$dashboard_secret_dir/session-secret"
)
```

Land the `dispatcher-dashboard-oauth` GSM mapping in a prerequisite change and
wait for `ci/dispatcher-dashboard-oauth` (key `session_secret`) to synchronize.
The serving certificates and injected CA are generated by OpenShift. Removing
an old GSM mapping does not itself revoke or delete an already deployed secret;
this configuration no longer consumes a shared observation secret.

## Publish both images before runtime manifests

Publish a dispatcher image that supports `--observation-api-listen-address`,
`--observation-api-service-account`, and the observation TLS certificate flags.
An image that only supports the former `--observation-api-token-path` cannot run
this configuration. The new observation listener remains disabled by default.

The standalone repository must contain the dashboard code, Makefile entry, and
image Dockerfile, including `--dispatcher-token-file` and `--dispatcher-ca-file`.
Land the image configuration and generated jobs separately from runtime manifests
if needed, run its main `images` postsubmit, and verify the promoted image using
normal CI registry credentials:

```sh
oc image info quay-proxy.ci.openshift.org/openshift/ci:ci_dispatcher-dashboard_latest
```

The image configuration builds amd64 and arm64. Both image publications, the
OAuth cookie secret, and the TokenReview permission are prerequisites for rollout.

## Enable and verify

Use the normal release review and GitOps process. A cluster administrator applies
the new observation authenticator RBAC before enabling the listener. No broader
`system:auth-delegator` role is required. The Service creates the dispatcher's
serving certificate, and the CA-injection ConfigMap must be present before the
dashboard starts. Normal retries handle asynchronous certificate provisioning.

Validate resource schemas first:

```sh
oc -n ci get secret dispatcher-dashboard-oauth -o name
oc create --dry-run=client --validate=true -f clusters/app.ci/prow/03_deployment/admin_prowjob-dispatcher_observation_rbac.yaml
oc create --dry-run=client --validate=true -f clusters/app.ci/prow/03_deployment/dispatcher-dashboard.yaml
oc create --dry-run=client -f clusters/app.ci/prow/03_deployment/prowjob-dispatcher.yaml -o json |
  jq 'if .kind == "List" then .items[] else . end | select(.kind == "Deployment" or .kind == "Service" or .kind == "NetworkPolicy")' |
  oc apply --dry-run=server -f -
```

A first-install server dry-run of new RoleBindings cannot resolve Roles that were
not persisted. Normal apply creates them in order. The dispatcher manifest also
contains unchanged override RBAC that some operators cannot reapply wholesale;
use GitOps rather than changing those permissions.

The dispatcher uses `Recreate`, so enabling the listener restarts it. After the
approved rollout, wait for both Deployments, generated certificates, and CA:

```sh
oc -n ci rollout status deployment/prowjob-dispatcher --timeout=5m
oc -n ci rollout status deployment/dispatcher-dashboard --timeout=5m
oc -n ci get secret prowjob-dispatcher-observation-tls dispatcher-dashboard-tls -o name
oc -n ci get configmap dispatcher-observation-ca -o name
oc -n ci get route dispatcher-dashboard
```

Open <https://dispatcher-dashboard-ci.apps.ci.l2s4.p1.openshiftapps.com>, complete
OAuth, and verify live overview, policy, overrides, and explicit job lookup. Select
**Collect logs** to check both components; an empty or limited sample is not a
health verdict. Readiness verifies local credentials, not upstream policy readiness.
Logged-out UI and diagnostics requests require OAuth. Only exact `/healthz` and
`/readyz` paths and the proxy's own health endpoint bypass login.

During rollout, verify anonymous requests and other ServiceAccounts cannot read
port 8443, other pods cannot reach that port through the network policy, and port
8080 still serves scheduling/monitoring without observation routes. No credentials
or tokens should appear in command output when performing these checks.
